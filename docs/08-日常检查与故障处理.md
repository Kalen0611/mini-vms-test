# MiniVMS 日常检查与故障处理

本文件提供适用于当前演练系统的人工检查步骤。日常检查命令供后续使用；除备份和业务查询外，未单独保存所有检查命令的执行结果。

## 1. 日常检查清单

| 检查项 | 操作 | 预期及解释 |
|---|---|---|
| 应用响应 | 请求 `/api/health` | HTTP 200；当前接口返回固定健康状态，不能单独证明数据库正常 |
| 数据库业务访问 | 请求 `/api/devices` | HTTP 200，列表及数量符合当前数据 |
| 端口 | 查看 8000 或 8001 的监听状态 | 应与当前运行的服务一致 |
| 日志 | 查看服务终端输出 | 根据请求状态码和异常信息定位问题 |
| 磁盘空间 | `df -h` | 确认数据库和备份所在文件系统有可用空间 |
| 备份文件 | 查看文件位置、时间及大小 | 核对最近一次实际备份时间；备份需定期恢复验证 |

在另一个 Ubuntu 终端运行，按需替换当前 WSL 地址和端口：

```bash
curl --fail --max-time 5 http://172.24.219.75:8000/api/health
curl --fail --max-time 5 http://172.24.219.75:8000/api/devices
ss -ltnp 'sport = :8000'
df -h
ls -lh ~/minivms-backups
```

本次原系统最终设备数为 2，恢复副本为 3。业务数据变化后，应同步更新预期，不能长期固定认为所有系统都应为 2。

## 2. 本次实际遇到的问题

### Linux 命令在 PowerShell 中执行失败

现象：提示符为 `PS C:\Users\Midori>`，`cd ~/projects/minivms-linux-demo` 提示路径不存在，`chmod` 无法识别。

原因：命令在 Windows PowerShell 中运行，而项目位于 Ubuntu 的 `/home/midori/projects`。

处理：执行 `wsl -d Ubuntu`，看到 `midori@qingsan:...$` 后执行：

```bash
cd ~/projects/minivms-linux-demo
ls -lh minivms.db
```

实际找到约 20 KB 的数据库，随后备份成功。

### 打开首页后只看到 JSON

现象：访问 8001 端口首页，显示应用名称、版本及 `status: running`。

原因：首页是应用状态接口，交互式接口页面位于 `/docs`。

处理：打开 `http://172.24.219.75:8001/docs`，随后成功执行设备和告警查询。

## 3. 其他故障排查参考

以下是排查方法，不表示这些故障均在本次实际发生过。

| 现象 | 排查顺序 |
|---|---|
| 页面无法连接 | 确认启动完成；核对 WSL 当前 IP、监听地址和端口；检查终端异常日志 |
| 端口已占用 | 用 `ss -ltnp` 确认占用者；确认是自己的旧服务后再决定停止或换端口 |
| 数据库不可写 | 核对数据库及所在目录的属主、写权限、磁盘空间；SQLite 还需要在目录中创建辅助文件 |
| `database is locked` | 排查未结束事务和并发写入，先保存错误及日志；不要直接删除数据库或辅助文件 |
| HTTP 403 | 核对请求头角色是否符合该接口要求；当前角色请求头不是安全登录授权 |
| HTTP 404 | 确认请求端口和实际记录 ID，先执行列表查询 |
| HTTP 409 | 检查设备 IP 与端口重复，或告警状态流转顺序 |
| HTTP 422 | 检查响应 `detail` 中的缺失字段、类型、范围及枚举值 |
| 恢复后数据不符 | 核对备份路径、备份时点、恢复目录和启动端口，先停止新增写入后排查 |

## 4. 测试数据隔离

现有设备、告警自动化测试会调用清空数据的函数。不要在保存演练数据的目录直接运行这些测试。后续应在独立项目副本执行，或改造为使用专门的临时测试数据库后再运行。
